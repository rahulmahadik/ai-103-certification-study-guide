Unit 2

What is AI?

"AI" is a broad word. In practice it means software that behaves in ways we think of as human: it understands what you give it, works something out, and answers. Underneath sit models trained on enormous amounts of data, which is where they pick up the sense of how words, images and sounds relate to each other. So an app can take input in almost any format, reason about it, and produce an answer or a prediction.

Exam angle: they give you a scenario and ask which capability fits. Match the input type (text / audio / image / document) to the capability.

Work out which of these your app actually needs and you have also worked out which Azure services to create. That is the entire point of this unit: capability first, service second.

Capability What to remember
Generative AI & agents
An LLM writes a new answer to a plain-language prompt. This is what chat apps run on. It is also the base for agentic AI: an agent is an LLM plus instructions (the job you are giving it) plus tools (things it can look up, and actions it can take).
Natural language processing
LLMs grew out of NLP rather than replacing it. NLP reads documents, email and social posts by counting and comparing the words in them, rather than writing new prose of its own. It still wins on cost for text analysis: term frequency, classification, sentiment, summarisation.
Computer speech
Understanding speech and producing it. Voice in, spoken answer out, through background noise, interruptions, many languages and accents. Also transcription, analysing recordings, reading aloud and live translation.
Computer vision
Making sense of images, video and live camera feeds, such as an automated grocery checkout. Modern models are multimodal, so they create images and video too, not just read them.
Information extraction
Borrows from all the others. Pull specific values out of documents, forms, images and recordings, the way an expenses system reads the date, line items and total off a scanned receipt.

Unit 3

Microsoft Foundry

Foundry is where AI development on Azure happens. Nothing stops you creating individual AI resources and calling them directly, and for a one-off script that is fine. But once a solution has more than a couple of moving parts, you want one place that holds your projects, the Azure resources behind them and your developer tools together. That is why Foundry is the recommended route for anything beyond the simplest build. It has two faces:

Foundry portal
A website you click through to work on your AI projects.
Foundry SDK
Libraries you call from code, so scripts and CI/CD pipelines can build the same things.

Projects & resources, the hierarchy that gets tested

Think of a project as the workspace for one solution: the connections it uses, its data, its code, and everything else built for it. Every project sits inside exactly one Foundry resource, and that resource is what actually supplies the compute, the storage and the AI tools. What you manage inside a project:

  • Models: models you have deployed from the Foundry Models catalog (Microsoft, OpenAI and others). Each deployment is an endpoint your code can call: use the project endpoint with the Foundry APIs and SDKs, or the Azure OpenAI endpoint with the OpenAI APIs and SDKs.
  • Agents: three things saved together under one name — a model, the instructions it follows and the tools it may use. You build them and call them through the Foundry Agent service, at the project endpoint.
  • Tools: the built-in ones (web search, code interpreter); your own or a third party's, plugged in over MCP (Model Context Protocol, the standard way a tool tells an agent what it can do); plus the Foundry Tools services (text analysis, speech, translation, content understanding). The Foundry resource hosts all of them, not the project.
  • Knowledge: your own data, pulled into the prompt so the model answers from it rather than from memory. Foundry IQ puts all of that data behind a single MCP connection, so you wire up one thing instead of many.
Remember this
Keep what belongs to one project apart from the shared cloud services in the Foundry resource. That split is the whole idea: every project draws on the same resource, so there is one thing to administer, and each team still owns its own work. Exam wording often contrasts this with the older hub-based (classic) project architecture. New architecture = a project on a Foundry resource; classic = a hub.

What you do in the portal

  • Find, compare, deploy and test models
  • Create and test agents
  • Create MCP connections to tools + Foundry IQ knowledge
  • Explore and test Foundry Tools
  • Manage resource configuration and user access
  • Get the endpoints and keys client apps need

Unit 4

Foundry Tools

Generative models get the attention, but plenty of everyday AI jobs already have a ready-made answer. Foundry Tools are exactly that: prebuilt APIs and models that ship with Foundry. Reaching for one instead of asking a generative agent to figure it out is usually cheaper and far more predictable.

Tool Use it for
Azure Language
 Reads text and tells you what is in it: entities (the names, places, dates and other things it mentions), sentiment, a summary. Also builds conversational language understanding models and question answering solutions.
Azure Speech
 Text to speech, speech to text, and live speech in real time for conversational apps and agents.
Azure Translator
 Translates text between a large number of languages, using up-to-date language models rather than fixed phrase rules.
Azure Document Intelligence
 Pulls fields out of invoices, receipts and forms. Use a ready-made model or train your own.
Azure Content Understanding
 One model, several content types: extract data from documents, images, video and audio streams.
Exam angle
How your app calls a tool: client app → the tool-specific endpoint in your Foundry resource → prove who you are, with the project authentication key or a Microsoft Entra ID token (token-based auth) → call that tool's own API or SDK. Some tools also give you a screen in the portal to configure and test them.
Naming history: Foundry Tools used to be called Azure AI Services, and before that Azure Cognitive Services. Both old names still turn up in APIs and SDKs. You can still create some of these tools as standalone Azure resources, but a new project should use the ones inside its Foundry resource.

Unit 6

Responsible AI, the six Microsoft principles

Two things make AI risky in a way ordinary software is not. It is probabilistic, so its answers reflect whatever it was trained on rather than a rule someone wrote down. And it sounds human, which makes people trust it more than they should. When it gets something wrong, or someone misuses it, real people are affected, so reducing that risk is part of the engineering job, not an afterthought.

Fairness
Treat all people fairly. A loan-approval model must not bias on gender or ethnicity. Tools can measure and reduce unfairness, but they are not enough on their own: check the training data is representative, and measure performance per subgroup throughout the lifecycle.
Reliability & safety
With self-driving cars or diagnostic models, unreliability costs lives. That means rigorous testing, controlled deployment, and sensible confidence-score thresholds, because the model only ever gives you a probability.
Privacy & security
Training data often holds personal details, and a live system keeps taking in more. Protect both the data and customer content, during training and in production.
Inclusiveness
The system should work for everyone, whatever their physical ability, gender, sexual orientation or ethnicity. The practical lever is who is in the room: get as broad a group as you can into design, development and testing.
Transparency
People should be able to understand the system: what it is for, roughly how it works, where it falls down. Tell them what affects accuracy, such as how many cases it trained on and which features weigh most heavily. Share confidence scores. And where personal data is involved, say how you use it, how long you keep it, and who can see it.
Accountability
People are accountable, not the software. The developers who trained and validated the model, and who wrote the logic around its decisions, carry that responsibility. They work inside a governance framework — written standards and sign-offs — that has to satisfy both your organisation's principles and the law.

Unit 2

Explore the model catalog

The model catalog is where you go to find and compare models. There are 1,900+ of them from many providers, so the filters matter as much as the list. Models fall into two groups, and the difference is who sells the model to you, which in turn decides how you are billed, whose licence you agree to and who supports it:

Foundry Models sold directly by Azure
Billed directly through your Azure subscription. Includes Azure OpenAI models as well as models from Microsoft and other providers.
Foundry Models from partners and community
Published by trusted partners and by the community, each on its own licence and its own pricing.

Each model has a model card showing its key information: the provider, capabilities, benchmark metrics, responsible AI considerations, and deployment options. You can search by keyword and filter on these attributes:

  • Collection: models provided directly in Azure, or models in the Hugging Face repository
  • Capabilities: reasoning (working a hard problem through step by step), tool calling (the model can call your functions and APIs), multimodal processing (it takes images and audio as well as text)
  • Source: the model provider, including Azure OpenAI, Microsoft, Cohere, Mistral, Meta, Anthropic and others
  • Inference tasks, meaning the job you want the model to do when it runs: text generation, summarization, translation, image generation, speech synthesis and other common AI tasks
  • Fine-tuning methods: supported techniques for fine-tuning a model
  • Industry: models trained on data from one industry, which usually beat a general-purpose model on that industry's own subject matter

Unit 3

Select models using benchmarks

Benchmarks exist so you can argue about models with numbers instead of opinions. Foundry sorts them into four buckets: quality, safety, cost and performance. Two places to look. The Model leaderboard ranks everything in the catalog against each other. A model card's Benchmarks tab zooms into one model across the datasets, with charts showing where it lands next to its peers.

Watch the direction of each metric. Quality scores are normalized 0 to 1 and higher is better, but the others do not all run that way. A lower ASR (attack success rate) means safer, because fewer attacks got through. Lower cost is better. Lower latency and lower TTFT (time to first token) are better. A higher F1 is better, because the model is catching more hate speech. A higher WMDP is worse, because the model knows more that could be dangerous.

Quality benchmarks

Quality benchmarks ask one question: are the answers accurate, coherent, and appropriate to what was asked? Every model goes through the same public datasets and is scored the same way, which is what makes the numbers comparable. The Quality index is the headline figure. It averages the accuracy scores from several of those datasets — reasoning, knowledge, question answering, mathematics and coding — into one number, and the higher it is, the better the model does across general-purpose language tasks. Datasets used include Arena-Hard (adversarial question answering), BIG-Bench Hard (reasoning capabilities), GPQA (graduate-level multi-discipline questions), HumanEval+ and MBPP+ (code generation tasks), MATH (mathematical reasoning), MMLU-Pro (general knowledge assessment) and IFEval (instruction following). Benchmark scores are normalized indexes ranging from zero to one, where higher values indicate better performance.

Safety benchmarks

Safety metrics measure how often a model produces harmful, biased or inappropriate content. They tell you where you stand; they do not stop anything by themselves. They matter most when the app is open to the public, in a regulated industry, or in front of customers.

Dimension and benchmark Metric and meaning
Harmful behavior detection
HarmBench		Measures how well a model holds out when someone tries to push it into an unsafe answer. The score is the Attack Success Rate (ASR), the share of those attempts that worked, so a lower ASR means a safer, more robust model. HarmBench tests three functional areas: standard harmful behaviors (cybercrime, illegal activities, general harm), contextually harmful behaviors (misinformation, harassment, bullying) and copyright violations (reproducing copyrighted material).
Toxic content detection
ToxiGen		Measures how well the model spots hate speech, including the implied kind. A higher F1 score means better detection across references to minority groups.
Sensitive domain knowledge
WMDP		Weapons of Mass Destruction Proxy. Measures what the model knows about biosecurity, cybersecurity and chemical security. A higher WMDP score means it knows more that could be dangerous.

Cost benchmarks

Foundry shows these only for serverless API deployments and for Azure OpenAI models.

  • Cost per input tokens: price for processing 1 million input tokens, the text you send to the model
  • Cost per output tokens: price for generating 1 million output tokens, the text the model produces
  • Estimated cost: combines input and output costs using a typical 3:1 ratio, three input tokens for every output token, giving one number for comparison. Lower values indicate more cost-effective models.

Performance benchmarks

  • Latency: mean (average seconds to process a request), P50 (median), P90, P95, P99, and time to first token (TTFT), the time until the first token arrives when streaming
  • Throughput: generated tokens per second (GTPS), total tokens per second (TTPS) for input and output combined, and time between tokens
  • The leaderboard summarizes performance using mean TTFT (lower is better) and mean GTPS (higher is better)
  • In an interactive app the user feels every second, so pay for high throughput and low latency. In batch processing nobody is waiting, so trade the speed away and choose on cost instead

Leaderboards and comparison features

  • Scenario leaderboards rank models one job at a time: reasoning, coding, math, question answering or groundedness. If your app is mostly one of those jobs, start from that leaderboard instead of going by the overall quality index alone.
  • Trade-off charts plot two metrics at once, such as quality against cost, throughput or safety. Models closer to the top-right corner perform well on both, and a slightly less accurate but significantly faster or cheaper model might serve you better.
  • Side-by-side comparison: check boxes next to two or three models, then choose Compare to see performance benchmarks (quality, safety, throughput), model details (context window, training data, supported languages), supported endpoints and feature support (function calling, structured output, vision).

Deploy models to endpoints

Deploying is what turns a model in the catalog into an endpoint your code can call. Each model lists the deployment types it supports, and the portal picks a sensible one for your environment automatically, so most of the time you are confirming rather than choosing. Use a Global Standard deployment in a Foundry resource whenever you can: it is the option with the most capabilities open to it.

Deploying a model, step by step

  1. From the portal homepage select Discover, then Models in the left pane, and open the model card to review specifications and supported deployment types.
  2. Select Deploy, then either Default settings (recommended configuration) or Custom settings.
  3. If the model requires an Azure Marketplace subscription (common for partner and community models), review the terms of use and select Agree and Proceed. Models sold directly by Azure, such as GPT-4o-mini, don't require this.
  4. Set the deployment name. It defaults to the model name; meaningful names help when you have several deployments of the same model. When your code calls the model, it passes this name in the model parameter, and that is what sends the request to this deployment rather than another one.
  5. Confirm the deployment type, which the portal selects automatically for the model and environment.
  6. For managed compute deployments, also configure the virtual machine SKU (you need Azure Machine Learning compute quota for that SKU) and the instance count, meaning how many copies run: more copies spread the load, and keep the service up if one of them fails.
  7. Select Deploy. You land in the Foundry Playground; verify the deployment status shows Succeeded.

Manage deployed models

Select Build, then Models in the left pane, to list the deployments in your resource. Open one to see:

  • Deployment configuration and status
  • Endpoint URL for API access
  • Authentication keys or tokens
  • Monitoring and usage metrics
  • Options to adjust deployment settings or delete the deployment

Three things your app needs

  1. Endpoint URL, the address your code sends requests to. Foundry offers two: a project endpoint when you want the Foundry-only features, and an OpenAI v1 endpoint when you want code written against the OpenAI APIs to work unchanged.
  2. Authentication key, the secret key or token presented on each request. Alternatively use Microsoft Entra ID authentication with an identity-based token, which is recommended for production.
  3. Deployment name, passed in the model parameter to route the request to your deployment.
In the playground
Test a deployed model straight away, without writing any code. Type prompts and read what comes back: simple questions, problems that need several steps of reasoning, requests for a particular format or style, and awkward edge cases that show you where the model gives up. Use the system message to set the context, the tone and the standing instructions that apply to every user input, for example "respond as a customer service representative". Then turn the dials: temperature (creative answers versus consistent ones), max tokens (how long the answer may be) and top-p (nucleus sampling: how wide a pool of likely next words the model may choose from). The Code tab shows authentication, endpoint configuration and request formatting in Python, C# and JavaScript, ready to copy into your application.

Unit 5

Evaluate model performance

Why bother evaluating at all? Four reasons. You want to find problems before your users do. You want the answers to actually satisfy people. You keep changing prompts and models, so you need to know whether each change helped or hurt. And you need evidence that the thing stays inside your policies on harmful content, privacy and data protection.

Manual evaluation approaches

  • Interactive testing in the playground means judging by eye: enter a wide spread of prompts and write down what you see — wrong facts, the wrong tone, instructions the model ignored. You can also run two models side by side, sending the same system instructions and the same prompt to both, so the comparison is fair.
  • Structured review is that same judgement, made repeatable. Write test cases that stand for what your users will really ask, then have people score every answer on relevance (does it address the request), informativeness (enough detail), engagement (appropriately conversational), accuracy (facts correct) and safety (avoids harmful, biased or inappropriate content). Scores usually run 1 to 5. Average them and you have a number for overall quality instead of an impression.
  • User studies collect feedback from actual or representative users, revealing confusing phrasing, missing context or unmet expectations that controlled testing misses.

Automated evaluation metrics

Generation quality metrics
  • Groundedness: does the answer stay with the source material you supplied, instead of the model filling the gaps by guesswork. Groundedness Pro answers yes or no — grounded or not grounded — which is what you want when the facts have to be right.
  • Relevance: does the response address the user's question appropriately.
  • Coherence: does it flow logically with consistent ideas.
  • Fluency: is the language correct, and does it read like something a person would write.
Risk and safety metrics
  • Self-harm content: responses discussing or encouraging self-harm
  • Hateful and unfair content: bias, discrimination, hateful statements
  • Violent content: containing or promoting violence
  • Sexual content: inappropriate sexual content
  • Protected material: potential copyright or proprietary content reproduction
  • Indirect attack (jailbreak): vulnerability to manipulation attempts
Defect rate
Content harm metrics are reported as a defect rate: out of all the responses, the percentage that scored at or above a severity threshold, usually Medium. For protected material and indirect attack, defect rate is calculated as (true instances / total instances) × 100. AI-assisted evaluation needs you to nominate a GPT model as the evaluator. That model then reads your deployed model's responses and scores them against the criteria you picked.

Natural language processing metrics

NLP metrics are mathematical, needing no evaluator model, but they usually need ground truth data, the expected or correct responses for comparison. Use them where there is one right answer, or a reference text to compare against. They fit badly on open-ended writing, where plenty of different answers are all good.

Metric What it measures and where it fits
F1-scoreHow many words the answer shares with the correct one, balancing precision (not adding wrong words) against recall (not missing important ones). Useful for classification and information retrieval.
BLEUBilingual Evaluation Understudy. Compares word sequences, or n-grams, between the generated text and the reference. The standard choice for machine translation.
METEORMetric for Evaluation of Translation with Explicit Ordering. Like BLEU, but it also accepts synonyms, word stems and paraphrases, so it judges less rigidly.
ROUGERecall-Oriented Understudy for Gisting Evaluation. Leans on recall rather than precision, which suits summarization: covering the key points matters more than trimming extra words.
GLEUGoogle-BLEU. A version of BLEU tuned for judging single sentences.

Create comprehensive evaluations

The portal's Evaluation feature runs systematic evaluations with test datasets and several metrics at once. Base the evaluation on one of:

  • Model: you supply the prompts, Foundry sends them to a deployed model during the run, and the answers that come back are what gets scored.
  • Agent: evaluate an agent's responses with user-defined prompts.
  • Dataset: evaluate pre-generated outputs already in your test dataset.

Dataset options when evaluating a model or agent: upload a new dataset as CSV or JSONL, use an existing dataset from the project, or generate a synthetic dataset where you specify the resource, number of rows and a prompt describing the data, optionally uploading files to improve relevance.

Then choose the metrics, map the columns in your data onto the fields the evaluation expects, set the system prompt, and start the job. It runs in the background, scoring each row against the metrics you chose. The results give you an overall score per metric, and the detail behind every test prompt.

Evaluator library

Open your project's Evaluation page and select the Evaluator library tab. There you can:

  • View Microsoft-curated evaluators for quality, safety and performance
  • Examine evaluator details: name, description, parameters, associated files
  • Read the annotation prompts behind the quality evaluators — the instructions the evaluator model is given — to see how each metric is worked out
  • Check definitions and severity levels for safety evaluators
  • Manage the evaluators you wrote yourself. Each one is versioned, so you can compare two versions, restore an older one, and share it with the rest of the team

Iterate on the results

If the scores come back lower than you need, work down this list. Each step costs more effort, and usually more money, than the one before it: prompt engineering (sharpen the instructions and the system message), a different model better suited to your use case, RAG to ground answers in your own data, then fine-tuning on your domain, where the model supports it.

If the safety metrics are the problem, you have three levers: content filters (Azure AI Content Safety), prompt hardening (safety instructions written into the system message), and output validation (your own code checks the response before anyone sees it). Set your evaluation benchmarks early and re-run them after every change, so you can see what the change bought you and catch anything it broke.

Explore with the model playground

The Model playground lives in the left navigation and is the fastest way to find out whether an idea works, because you write no code to try it. Type a prompt, watch the answer come back, then start turning dials: temperature, max tokens, and the system message that shapes how the model behaves. Swap models and repeat.

Samples come pre-populated with your project endpoint, model deployment name and current settings, ready to copy into your development environment.

The typical workflow: explore in the playground to find what works, generate code samples from the Code tab, develop the application from that code, then iterate by returning to the playground to test new ideas and updating your code.

Your first session in the playground
  1. Deploy a model first. The playground has nothing to talk to until a deployment exists.
  2. Write the system message before the prompt. It is the part you will ship; the prompt is throwaway.
  3. Move one dial at a time. Change temperature and the system message together and you learn nothing from the result.
  4. Keep the prompts that failed. Those are the start of the evaluation set you will need in module two.
  5. Press Code before you leave. It writes out your endpoint and deployment name, so you do not copy them by hand.

Choose an endpoint and SDK

Four decisions to make before you write any code.

  1. Endpoints: every Foundry project gives you two addresses to call, a Project endpoint and an Azure OpenAI endpoint, and either one reaches the things inside the project, such as your model deployments.
  2. Client SDK: which library you use follows from the endpoint you chose, either the Microsoft Foundry SDK or the OpenAI SDK. Each one hands you a client object that speaks the OpenAI API and sends prompts; what differs is the extra work each can do.

Unit 4

Generate responses with the Responses API

The Responses API merges what used to be two separate APIs, ChatCompletions and Assistants, into one. The important word is stateful: it remembers the conversation for you, which is exactly what a chat app needs. You call it through an OpenAI-compatible client from either SDK. What you get: stateful conversations, so context carries from one turn to the next without you resending it; a unified experience, because the chat completions and Assistants ways of working are now one API; support for Foundry direct models, the ones hosted in Foundry rather than only the Azure OpenAI ones; and simple integration, since you call it with the same OpenAI-compatible client you already have. It is the recommended approach and replaces the older ChatCompletions API for most scenarios.

A simple response

response = openai_client.responses.create(
    model="gpt-4.1",   # deployment name
    input="What is Microsoft Foundry?"
)
print(response.output_text)

The input parameter takes a text string containing your prompt. Response object properties worth knowing: output_text (the generated text), id (unique identifier), status (for example "completed"), usage (input, output and total tokens) and model.

Add instructions, often called the system prompt, to guide behaviour, and control generation with temperature (randomness, 0.0 to 2.0; higher is more creative and varied), max_output_tokens (maximum tokens in the response) and top_p (an alternative to temperature for controlling randomness).

Instructions plus parameters

response = openai_client.responses.create(
    model="gpt-4.1",
    instructions="You are a helpful AI assistant "
                 "that answers clearly and concisely.",
    input="Write a creative story about AI.",
    temperature=0.8,
    max_output_tokens=200
)

With the Foundry SDK or AzureOpenAI client against a project endpoint, the same call works with Foundry direct models such as Microsoft Phi or DeepSeek, by passing that deployment name, for example model="microsoft-phi-4".

Multi-turn conversations

Chain turns with previous_response_id: you send back the id of the last response, and the service puts that earlier exchange into the context of the new one, so the model can follow the thread. In a real app this becomes a loop:

last_response_id = None
while True:
    input_text = input('\nYou: ')
    if input_text.lower() == "quit":
        break
    response = openai_client.responses.create(
        model=model_name,
        instructions="You are a helpful AI assistant.",
        input=input_text,
        previous_response_id=last_response_id
    )
    print("\nAssistant:", response.output_text)
    last_response_id = response.id

Manual chaining is the alternative: build the message history yourself as a list of {"type": "message", "role": ..., "content": ...} items, append response.output after each turn, and pass the whole list as input. Use it when you need to pick exactly which messages go into the context, drop older turns yourself to stay under the token limit, or save the history to a database and load it back later.

The API also keeps response history, so openai_client.responses.retrieve(response_id) fetches an earlier response.

Context window warning: keeping history costs tokens. Everything the model sees on a single run can include the system instructions and safety rules, the current prompt, the conversation so far, the tool schemas (functions, OpenAPI specs, MCP tools), whatever the tools returned (search results, code interpreter output, files) and anything pulled from memory stores, RAG or file search. All of that is joined together, turned into tokens and sent again on every request. The SDK keeps track of the conversation for you; it does not make the conversation cheaper.

Streaming, for responsiveness

Generation time depends on the model, context window size and prompt size, and users get frustrated if the app appears to freeze. Streaming delivers output incrementally:

stream = openai_client.responses.create(
    model="gpt-4.1", input="...", stream=True)
for event in stream:
    if event.type == "response.output_text.delta":
        print(event.delta, end="")
    elif event.type == "response.completed":
        response_id = event.response.id

Async, for concurrency

An asynchronous client does not block: your code carries on with other work while a call is still in flight. That is what you want in a high-performance app, where a request may take a while to come back or many requests are running at once. Import AsyncOpenAI instead of OpenAI and await each call; async streaming works the same way with async for.

client = AsyncOpenAI(base_url=..., api_key=token_provider)

async def main():
    response = await client.responses.create(
        model="gpt-4.1",
        input="Explain quantum computing briefly.")
    print(response.output_text)

asyncio.run(main())

Generate responses with the ChatCompletions API

ChatCompletions is everywhere, across models and platforms alike. Start new work on Responses, but you will still meet this one whenever you maintain existing code or need something that runs on more than one platform. A prompt here is a list of JSON message objects, each carrying a role, meaning system, user or assistant, and its content.

The key difference to remember: unlike the Responses API, ChatCompletions keeps nothing between calls; there is no stateful response tracking on the server. If the model is to know what was said earlier, your code has to hold the record itself: append each user message and each assistant reply to the message list, then send that whole list again on every turn.

It does less than Responses, but it is in use nearly everywhere, so knowing your way around it pays off.

conversation_messages = [
    {"role": "system",
     "content": "You are a helpful AI assistant."}
]
while True:
    input_text = input('\nYou: ')
    if input_text.lower() == "quit":
        break
    conversation_messages.append(
        {"role": "user", "content": input_text})
    completion = openai_client.chat.completions.create(
        model="gpt-4o",
        messages=conversation_messages
    )
    assistant_message = completion.choices[0].message.content
    print("\nAssistant:", assistant_message)
    conversation_messages.append(
        {"role": "assistant", "content": assistant_message})
Exam angle
Know which API and client each scenario needs. Stateful multi-turn chat with the least code points to Responses with previous_response_id. Existing OpenAI code that must keep working points to ChatCompletions with the OpenAI SDK. Agents, evaluations, tracing or connections point to the Foundry SDK and AIProjectClient. Production authentication points to Microsoft Entra ID, never a key in code. Response text comes from response.output_text for Responses and completion.choices[0].message.content for ChatCompletions.

What are tools?

Some models in the catalog can do more than talk: they can go and find something out, or carry out a task. You switch that on by listing the tools the model is allowed to use in the prompt you send through the Responses API. So the path is simple enough: filter the catalog for a model with tool calling, deploy it, then have your app send prompts with the tool list attached.

By default the model chooses when to use a tool and which one, based on the prompt. You can configure tool selection rules and use the Instructions (system prompt) parameter to guide that choice.

Tools are passed as a JSON list to responses.create(), each entry having a "type" plus tool-specific settings. These four are not the whole list, and new tools for agents keep arriving.

Tool What it gives the model
code_interpreterA Python sandbox the model can write and run code in.
web_searchSearches the internet, so answers can be newer than the training data.
file_searchSearches files you upload, indexed for vector search, so answers come from your content.
functionCalls functions in your own code.

Unit 3

code_interpreter

Hands the model a Python runtime it can write into and execute mid-conversation. The difference matters: instead of describing what the code would do, it runs the code and comes back with the real answer.

Key features: it writes Python and runs it there and then, inside a sandbox; it works with files, taking in a CSV, JSON or image, processing it and giving one back; it does real data work, meaning calculations, statistics and reshaping; it sees what its own code printed, errors included, so it can try again; and it solves problems that need actual computation, such as maths, simulations and logic puzzles.

Use cases: data analysis (parse a CSV and generate summary statistics), maths and physics (differential equations, physics simulations), file conversion (JSON to CSV and back), prototyping (test algorithms before formal implementation).

response = client.responses.create(
    model=model_deployment,
    instructions="You are an AI assistant. Use the "
                 "python tool to run code for math problems.",
    input="What is the square root of 16?",
    tools=[{"type": "code_interpreter",
            "container": {"type": "auto"}}]
)
print(response.output_text)

The flow: you send a request with code_interpreter in the tools array; the model decides whether it needs to run code; it writes the Python; the code runs in a sandbox stocked with common libraries such as pandas, numpy and math; and the output goes back to the model, which folds it into the answer.

Best practices
  • Be specific about data format and expected output. Many models internally call this the python tool, so use that language in your instructions.
  • Provide context: relevant domain knowledge in the prompt
  • Validate results: review AI-generated code before production use
  • Monitor costs: execution adds tokens, complex operations use more resources
  • Use the libraries: pandas, numpy and matplotlib are already installed
  • Error handling: the model sees errors and attempts fixes automatically
Limitations
  • Runs in a sandboxed environment with no external network access
  • Some libraries may not be available; tell the model if a standard library fails
  • Timeout limits apply to long-running operations
  • Memory constraints: massive datasets may need streaming or chunking

Unit 4

web_search

Lets the model go and look something up while it is answering. Rather than leaning on training data alone, it runs a search, reads what comes back, and builds the answer from current sources. Worth reaching for whenever the facts move: pricing, product releases, policy changes, anything in the news.

Key features: it fetches information as it stands today; its answers are grounded in the sources it found; it hallucinates less, because it is checking outside sources rather than recalling from training; it writes its own search queries, deciding when to search and what to search for from what you asked; and it all happens in a single call, so searching and answering are one step as far as your code is concerned.

Use cases: current events (summarise a breaking announcement), market research (compare recent features or pricing across vendors), policy monitoring (has guidance changed), fact verification (validate claims against reputable public sources).

response = client.responses.create(
    model=model_deployment,
    instructions="You are an AI assistant. Use web "
                 "search when current information is required.",
    input="What are three major announcements "
          "from Microsoft Build this week?",
    tools=[{"type": "web_search"}]
)

The flow: you include a web search tool in the tools array; the model works out whether it needs fresh facts; it sends one or more search queries; it picks the pages worth reading and summarises them; then it writes the final answer from what it found.

Best practices
  • Ask time-aware questions clearly, using words like "latest" or "current", or date ranges
  • Set expectations for sources: prompt for reputable or official sources when accuracy matters
  • Request concise outputs, short summaries with key points, to reduce noise
  • Verify critical facts independently in high-stakes scenarios
  • Track usage and latency, since web retrieval increases response time and token usage
Limitations
  • Results depend on what is publicly available and indexable at query time
  • Source quality varies, so output may still need human review
  • Retrieved content changes over time, so repeated runs can produce different answers
  • Some environments apply regional, policy or network restrictions to web access

file_search

Points the model at your own material instead of the open web: policy documents, manuals, contracts, whatever your internal knowledge lives in. It searches the indexed content of those files and answers from what it finds.

Key features: answers grounded in the files you uploaded; semantic retrieval, which finds passages by meaning rather than by exact keyword; a search that can span one vector store or several at once; citations, plus the matched passages themselves if you ask for them, so you can see why it answered as it did; and answers that fit your organisation, because they come from your organisation's own material.

Use cases: policy Q&A from HR PDFs, support assistants retrieving product steps from troubleshooting guides, legal review locating clauses across contracts, knowledge discovery summarising technical documentation sets.

vector_store = client.vector_stores.create(
    name="policy-docs")
client.vector_stores.files.upload_and_poll(
    vector_store_id=vector_store.id,
    file=open("expenses_policy.pdf", "rb"))

response = client.responses.create(
    model=model_deployment,
    instructions="You are an AI assistant that provides "
                 "information from HR policy documents.",
    input="What's the maximum amount I can claim "
          "for a taxi ride?",
    tools=[{"type": "file_search",
            "vector_store_ids": [vector_store.id]}],
    include=["file_search_call.results"]
)

The flow: you upload documents to a vector store; you include file_search in the tools array with the vector store IDs; the model searches the indexed chunks; the passages that match are added to the prompt; and the model writes its answer from those passages.

Best practices
  • Use high-quality source files: clean, current documents improve retrieval accuracy
  • Write focused prompts to reduce ambiguous matches
  • Scope vector stores carefully, separating domains such as HR, legal and finance
  • Include retrieval results during development for troubleshooting
  • Keep human validation for critical workflows
Limitations
  • Answer quality depends on document quality, coverage and chunk relevance
  • Very large or mixed-domain stores return less focused context
  • Updated source files may need re-indexing before new content is searchable
  • Retrieval improves grounding but doesn't replace human review for sensitive decisions
How it scales
file_search is the right way to ground a model in a specific set of documents or data files. For enterprise-scale agents needing large quantities of data across multiple data stores, use a Foundry IQ knowledge base with a Foundry agent instead. Unit 6

function (function calling)

Lets the model decide when to reach for one of the functions you have exposed. The part people get wrong: the model never runs your code. It hands back a structured request saying which function and with what arguments, your application executes it, and you feed the result back in. That handshake is what connects the model's reasoning to real systems, your APIs, your database, your workflows.

Key features: the model asks in a fixed, machine-readable shape, naming the function it wants and the arguments to pass; you keep control of execution, so your app decides where and how the code runs; the same pattern covers your APIs, your internal services and small helper utilities; the exchange can run over several turns, because you hand the tool's output back and the model carries on reasoning from it; and the answers are grounded in live data straight out of your own systems.

Use cases: system integration (call an internal API for account or order details), task automation (trigger ticket creation or notifications), data lookup (query business rules or reference tables before answering).

function_tools = [{
    "type": "function",
    "name": "get_time",
    "description": "Get the current time"
}]

response = client.responses.create(
    model=model_deployment,
    input=messages,
    tools=function_tools)
messages += response.output

for item in response.output:
    if item.type == "function_call" and item.name == "get_time":
        messages.append({
            "type": "function_call_output",
            "call_id": item.call_id,
            "output": get_time()})
        response = client.responses.create(
            model=model_deployment,
            instructions="Answer only with the tool output.",
            input=messages,
            tools=function_tools)
print(response.output_text)
The six-step flow
  1. You define tools in the tools array
  2. Model evaluates whether a call is needed
  3. Model asks for the call, naming the function and giving the arguments and a call id
  4. Your app runs the matching function
  5. You return a function_call_output item with the result
  6. Model completes the answer using the tool result
Best practices
  • Keep tools focused: small, single-purpose functions are easier to control and test
  • Validate function inputs, never trust tool arguments blindly in production
  • Handle errors safely, returning clear error outputs the model can reason about
  • Log tool usage: calls, latency, failure rates
  • Limit sensitive operations, requiring explicit authorization for high-impact actions
Limitations
  • The model requests calls, your application must run them
  • Incorrect or unexpected tool arguments can occur and should be validated
  • Tool latency increases end-to-end response time
  • Function calling improves reliability, but outputs still need review for critical decisions

Unit 2

Optimize model output with prompt engineering

The cheapest lever you have, and the one to pull first: write better prompts. No infrastructure to stand up, no training data to gather, just careful wording. Prompts for chat completion models typically include a system message (instructions defining behaviour, role and constraints), a user message (the question or input), assistant messages (previous responses, in multi-turn conversations) and examples (sample input and output pairs showing the expected format).

System messages

They appear first in the conversation and act as the highest-level instructions. Use them to define the assistant's role and boundaries, set tone and communication style, specify output formats such as JSON or bullet points, and add safety and quality constraints. A system message influences but does not guarantee compliance: the model usually does what it says and sometimes will not, so test it, revise it, and back it up with content filtering and evaluation.

Design checklist: start with the assistant's role and the expected outcome for a typical request; define boundaries by listing topics, actions and content types to avoid; specify the output format plainly and keep it consistent; add a "when unsure" policy telling the model what to do when the request is ambiguous, out of scope, or when it lacks information.

Model parameters

  • Temperature: randomness of the output. Higher, for example 0.7, gives more creative and varied responses; lower, for example 0.2, gives more focused and deterministic ones. Low for factual tasks, higher for creative.
  • Top_p: also called nucleus sampling. It limits the model to the smallest set of next tokens whose probabilities add up to the value you set. At a top_p of 0.9 the model ranks the candidates and keeps taking them until their combined probability reaches 90% — often only a handful of tokens, not 90% of the vocabulary.

General recommendation: adjust either temperature or top_p, not both at once. Models are also susceptible to recency bias, so text near the end of a prompt can carry more influence; if instructions aren't followed consistently, repeat the key instruction at the end.

Prompt patterns

Pattern What it does
PersonaGive the model a role, for example "you are a marketing professional writing for technical customers". The same question then produces a far more audience-aware answer.
Format templateHand it a template so the output arrives in a fixed shape, for example hotel name, location, star rating, price per night. Consistent output is far easier to parse.
Chain of thoughtAsk for the reasoning step by step. Fewer wrong answers, and you can check the logic. A cousin of this is breaking the task down: pull out the key facts first, then answer from them. Only for non-reasoning models, since reasoning models already do this internally.
Few-shot learningShow examples of input and output so the model copies the pattern. One example is one-shot, several are few-shot, none is zero-shot. Classic use is classification: the examples teach the labels.
Clear syntax and delimitersWhen a prompt mixes instructions, source text and examples, separate them with ---, Markdown headings or XML tags, so the model can tell an instruction from content.
Where this stops working
Prompt engineering is right when you need to guide tone, format and behaviour, give task instructions, iterate quickly without infrastructure changes, and keep costs low. Its limits are the exam's favourite trigger: if the model lacks the information it needs, such as your company's hotel catalog, you need RAG; if it consistently fails to hold a behaviour despite detailed instructions, you need fine-tuning.

Unit 3

Ground your model with Retrieval Augmented Generation

Every model was trained up to a date, and none of them were trained on your company's private data. A model missing that context does not go quiet, it produces something that reads perfectly well and happens to be wrong. Grounding is the fix: hand it the facts to answer from. RAG is how that is usually done. Ungrounded, the model relies only on training data and might invent hotel names; grounded, it receives your actual catalog data and answers with real names, prices and availability. If you would rather build one than read about one, this Python RAG walkthrough works the same pattern end to end.

The three RAG steps:

  1. Retrieve: search a data source for information relevant to the question.
  2. Augment: add the retrieved information to the prompt as context.
  3. Generate: send the augmented prompt to the model to generate a grounded response.

Embeddings and vector search

An embedding is a piece of text turned into a vector: a long list of numbers that between them stand for what the words, the sentence or the whole document mean. You create them by sending content to an embedding model, such as an Azure OpenAI embedding model in Foundry. Two sentences with different words but similar meaning, "The children played joyfully in the park" and "Kids happily ran around the playground", produce vectors that sit close together in multidimensional space.

Cosine similarity measures how close two vectors are by calculating the angle between them; a value near 1 means very similar. That is what lets retrieval find relevant documents when the exact words don't match.

Azure AI Search as the retrieval component

  1. Add your data to Foundry from Azure Blob Storage, Azure Data Lake Storage Gen2 or Microsoft OneLake; you can also upload files directly.
  2. Create an index: an embedding model turns your content into vectors, and Azure AI Search stores the index that holds them.
  3. Query the index when a user asks a question: your app turns the question into an embedding, the index finds the content whose vectors sit closest to it, and those results come back for you to use.

Search techniques: keyword (the exact terms have to match), semantic (a language model judges how well a result answers the question, so wording that means the same thing still matches), vector (question and content both become embeddings, and the nearest ones win) and hybrid, which combines all three. Hybrid search is recommended for generative AI applications.

Unit 4

Fine-tune a model for consistent behavior

Sometimes you have written a careful system message, added examples, and the model still drifts. That is the point at which fine-tuning earns its cost: you train a pretrained model further on a smaller dataset of your own, which nudges its internal weights until its answers follow your patterns. It uses LoRA (Low-Rank Adaptation): rather than rewrite every weight in the model, LoRA learns a small extra set of numbers that closely approximates the change, and it touches only the parameters that matter most. Training comes out faster and cheaper, and quality holds up. Compared with training from scratch you need less time, fewer compute resources and significantly less data. Fine-tuning is an advanced capability: always evaluate a standard model's baseline first, or you cannot tell whether fine-tuning improved or degraded performance.

When to fine-tune

  • Consistent style and tone: a specific brand voice followed reliably across all interactions
  • Specific output formats: reliable structured output such as JSON to a defined schema, where few-shot examples aren't sufficient
  • Reducing prompt length: long system messages with many examples consume tokens and add latency; fine-tuning embeds those patterns in the model
  • Distillation: teach a small model to answer like a big expensive one. Collect the big model's outputs, fine-tune the small model on them, and you get close to the same quality for less money and less waiting
  • Enhancing tool usage: fine-tuning with tool examples improves tool selection and parameter generation accuracy

Three fine-tuning techniques

  • Supervised fine-tuning (SFT): train on a labeled dataset of prompt-and-response pairs, so the model matches those patterns. Best when there are clear, well-defined ways to approach a task.
  • Reinforcement fine-tuning (RFT): improve behaviour round after round. A grader scores each answer, better answers are rewarded, and the model shifts a little towards them each time. Suits complex or changeable tasks that have many acceptable solutions, where what you want is better reasoning.
  • Direct Preference Optimization (DPO): show the model pairs of answers, one marked preferred and one not, so it learns which kind people want. It needs less compute than traditional reinforcement learning and aligns the model just as well.

Techniques combine: SFT first to create a customized model, then DPO to align responses further to your preferences.

Training data

High-quality examples in JSONL format. For chat completion models each line is a conversation with system, user and assistant messages:

{"messages": [
  {"role": "system", "content": "You are a friendly travel advisor for Margie's Travel."},
  {"role": "user", "content": "I need a budget hotel in Tokyo."},
  {"role": "assistant", "content": "Here are some great budget-friendly options..."}
]}
  • Include a consistent system message across examples; leaving it blank tends to produce lower-accuracy models, and use the same system message at inference
  • Use high-quality, representative examples covering the range of expected scenarios
  • Aim for at least hundreds of examples; more is generally better
  • Assistant responses must reflect exactly the style, format and tone you want

Challenges to weigh

  • Training costs: upfront training cost plus ongoing hourly cost for hosting the custom model
  • Data quality: poor or unrepresentative data leads to overfitting, underfitting or bias
  • Maintenance: retraining may be needed when data changes or updated base models are released
  • Experimentation: finding the right hyperparameters (epochs, batch size, learning rate) takes testing and iteration
  • Model drift: specializing too narrowly makes the model less effective at general language tasks outside the fine-tuned domain. The word also appears in monitoring, where it means a deployed model’s behaviour shifting from its baseline over time

Unit 5

Compare and combine optimization strategies

These are not rivals. They fix different problems, and it helps to think of two separate axes. Optimize for context when the model does not know something it needs to know, such as your own domain, and accuracy is what you are chasing. RAG is the answer there, because it fetches the relevant data from outside the model at the moment of the question. Optimize the model when it knows enough but will not hold a format, style or tone from one answer to the next. Fine-tuning is the answer there, because you train it on examples of the output you want. Prompt engineering sits under both: it tells the model how to behave and what to pay attention to, and you add RAG or fine-tuning at the point where the prompt alone stops being enough.

Decision framework, in order: start with prompt engineering (system messages, few-shot examples, parameter tuning) and evaluate; add RAG if the model needs specific, current or private data to answer correctly; add fine-tuning if style, tone or format is unreliable despite detailed prompts; combine only as your requirements demand, since not every application needs all three.

Units 2 and 3

Plan the solution, then map potential harms

Mapping comes first, and it runs in four steps: work out what could go wrong, decide which of those matter most, prove they actually happen, then write it down and tell the people who need to know.

1. Identify. Which harms are relevant depends on what you built the solution out of: the services and models that generate the output, and any fine-tuning or grounding data you used to customize it. Three come up again and again: output that is offensive, pejorative or discriminatory; output that states things which are simply not true; output that encourages or supports illegal or unethical behaviour. Someone has usually written the known limitations down already, so go and read them: the Azure OpenAI Service transparency note, and whatever the model's developers publish themselves, for example the OpenAI system card. The Responsible AI Impact Assessment Guide and template are how you document harms.

2. Prioritize. For each harm, judge two things: the likelihood that it happens at all, and the level of impact if it does. Then sort the list so the harms that are both likely and damaging come first. When you sort, weigh what the solution is meant to be used for and how someone might deliberately misuse it. There is no formula here; the ordering is a judgement call. Take the smart kitchen copilot. A recipe for a lethal poison does far more damage than a wrong cooking time, but wrong cooking times will happen far more often. Which of the two goes at the top is a decision the team argues out, sometimes with policy or legal experts in the room.

Red teaming
3. Test and verify. Test the solution to confirm that the harms on your list really do happen, and to find out under what conditions. Testing also turns up harms nobody thought to list. The standard approach is red team testing: testers set out to break the thing on purpose, probing for weaknesses and trying to make it produce harmful output. In the kitchen copilot, that means asking it for poison recipes, or for a quick recipe using ingredients that must be thoroughly cooked. Write down every attempt that worked, then read the collection back and use it to judge how likely harmful output really is once real users arrive. Red teaming extends an existing cybersecurity practice into responsible AI.
Write it down
4. Document and share. Hand the evidence to the people who need it, and keep the prioritized list alive as new harms turn up.

Unit 4

Measure potential harms

What you are after is a baseline: a number for how often your solution produces each harm today. Without it you cannot tell whether any later mitigation actually helped. Three steps:

  1. Prepare a diverse selection of input prompts, chosen because they are likely to produce each harm you documented. If one harm is that the system could help manufacture dangerous poisons, write prompts likely to elicit exactly that.
  2. Submit the prompts to the system and retrieve the generated output.
  3. Apply pre-defined criteria — criteria written down before anyone looked at the output — to sort each response by how harmful it is. The categories can be as simple as harmful or not harmful, or a scale of harm levels, but the criteria must be strict, and everyone must apply them the same way every time.

Document and share the measurement results with stakeholders. Start manual on a small set of inputs, to confirm results are consistent and criteria well defined, then automate for larger volumes, possibly using a classification model to evaluate output. Even once it is automated, keep testing by hand from time to time: to cover scenarios the automation has not seen, and to confirm it is still scoring output the way you would.

Unit 5

Mitigate potential harms, four layers

No single control catches everything, so mitigation is layered, with something to do at each of four levels. Once you have changed anything, test again and compare against the baseline you recorded earlier.

1. Model
The generative models at the heart of the solution. Mitigations: select a model appropriate for the intended use, since a simpler model may do everything the job needs while being less likely than a powerful one to generate something harmful; and fine-tune a foundation model on your own training data, so its answers stay relevant and stay inside the scenario you built it for.
2. Safety system
The settings the platform itself gives you, switched on around the model rather than built into it. Foundry calls them guardrails: checks that sit on both sides of the model and can suppress a prompt on the way in or a response on the way out. The main one is a content filter, which sorts what it sees into four categories of potential harm — hate and fairness, sexual, violence and self-harm — plus a fifth guardrail category, task-adherence. The first four are each graded at one of four severity levels — safe, low, medium, high — and you choose the severity at which the filter starts blocking. Task-adherence is the odd one out: it watches how the agent behaves rather than what the content says, and catches an agent that drifts off its instructions or calls a tool it should not have called. Guardrails also include prompt shields, which run abuse detection algorithms over what comes in to spot someone systematically attacking the solution, for example a user trying to talk the model out of its system prompt.
3. System message and grounding
How you build the prompt before the model ever sees it. Write a system message that spells out how the model should behave and what it must not do. Use prompt engineering to add grounding data to the prompt, which makes the answer both more relevant and less likely to be harmful. And use a RAG approach to fetch that grounding data from sources you trust at the moment the question is asked.
4. User experience
The app people actually type into, plus the documentation and other material that goes out with it. Design the interface to constrain inputs to particular subjects or formats rather than accepting anything at all, and apply input and output validation on top of that. The documentation must be honest about what the solution can do, what it cannot, which models sit underneath, and which harms your mitigations may still fail to catch.

Unit 6

Manage a responsible generative AI solution

Prerelease reviews

Work out what your organization and your industry require you to comply with, then give the teams that own those requirements time to review the system and its documentation before it ships. Common reviews: legal, privacy, security, accessibility.

Release and operate

  • Phased delivery plan: release first to a restricted group of users to gather feedback and find problems before a wider audience
  • Incident response plan, including estimated response times for unanticipated incidents
  • Rollback plan defining the steps to revert to a previous state
  • Ability to immediately block harmful system responses when discovered
  • Ability to block specific users, applications or client IP addresses in the event of misuse
  • A way for users to give feedback and report issues, specifically to report content as inaccurate, incomplete, harmful, offensive or otherwise problematic
  • Telemetry, so you can see whether users are satisfied and where the solution is missing something or is awkward to use, collected in compliance with privacy laws and your own policies

Skill area 1

Build retrieval and grounding pipelines

Before an agent can retrieve anything, somebody has to get the content in. This is the ingestion half of RAG: how documents arrive, what happens to them on the way in, and how they are queried once they are there. Part 5 covered the query side; this is the pipeline that fills the index it queries.

The indexer pipeline, stage by stage

Stage What it does
Data sourceWhere the content already lives — Blob Storage, Azure SQL, Cosmos DB. You point at it; you do not copy it first.
IndexerThe job that pulls from the data source, on demand or on a schedule. It begins with document cracking: opening each file and pulling out the text. Images are a separate, chargeable opt-in — image extraction is disabled by default and is switched on with the indexer's imageAction parameter.
SkillsetA list of enrichment steps attached to the indexer. Built-in skills come from Microsoft — OCR for images, text split for chunking, language detection, entity recognition, key phrase extraction. A custom skill is your own code behind a web API, called in exactly the same way, for the enrichment nobody ships.
IndexThe searchable result. Two mappings decide what reaches it: field mappings carry a raw source field straight through, and output field mappings carry something a skill produced. The two are not equally optional: a source field whose name and type already match a field in the index arrives without a field mapping, but anything a skill produced and you did not give an output field mapping is discarded when the run ends.
Knowledge storeOptional. Projects the same enriched output into tables or blobs, for tools that want the structured data rather than a search index.
Why it matters
Skills write into an in-memory enrichment tree that lives only for the length of the run. A skill can produce a perfect result and still leave the index empty, because nothing mapped its output to a field. If a scenario says the enrichment works but the field is blank, the answer is the output field mapping, not the skill.

Chunking, and why it comes first

  • The Split skill breaks long text into pages of roughly 5,000 characters, or into sentences. When you are chunking, it is normally the first skill in the set, because the skills after it work better on a paragraph than on a whole report.
  • Chunk before you embed. One vector for a forty-page document is an average of everything in it, so it sits near nothing in particular and matches nothing well.
  • Integrated vectorization is two halves. At indexing time it does the chunking and the embedding inside the pipeline, so there is no separate job to write and no second copy of the text to keep in step. At query time a vectorizer, declared in the index schema and assigned to the vector field, turns the incoming question into a vector for you; it has to match the embedding model that encoded the content.

OCR in the ingestion flow

A scanned PDF or a photographed page has no text layer, so a plain indexer finds nothing to index. Two things have to be set. In the indexer configuration, set imageAction to generateNormalizedImages, which puts the page images into the enrichment tree at /document/normalized_images; then add the OCR skill to the skillset with that path as its image input. It reads the pixels, after which the text is chunked, embedded and indexed like any other. Leave imageAction at its default of none and the skill has nothing to read. That is the whole of the “RAG ingestion flow including OCR” objective: OCR is a step in the pipeline, not a separate product you call first.

Layout, markdown, and the things an indexer cannot read

The objective asks for enrichment across text, images and layout, and for analyzers that produce structured or markdown output. Those are two named skills and one service.

  • The Document Layout skill (Microsoft.Skills.Util.DocumentIntelligenceLayoutSkill) runs the Document Intelligence layout model over a file and hands back its structure. Set outputFormat to markdown — the default — and you get the document as headed Markdown sections, which is what the objective means by markdown output and what a model reads far better than a wall of text. Set it to text and you get chunks instead, sized by chunkingProperties, with an overlap you choose.
  • Chunking on headings rather than on a character count keeps a section whole, so a retrieved chunk is a complete thought rather than the back half of one.
  • An indexer reads documents and images. It does not transcribe audio or video — there is no skill that does. For media, the route is Content Understanding, whose analyzers take documents, images, audio and video and return the fields you asked for; you then index what comes back.
  • Built-in skills that call another service are billable. You get 20 documents per indexer per day free, and past that the skillset needs a Microsoft Foundry resource attached to bill against. Text Split is free because it calls nothing.
Querying it
The objective also lists semantic, hybrid and vector search under this skill area. Those are the query side of the same index, and Part 5 covers them: keyword matches terms, vector matches meaning, semantic re-ranks what came back, and hybrid runs them together. Hybrid is the recommended mode for grounding.

Handing the index to an agent

  • The finished index becomes a knowledge source. Knowledge sources are gathered into a knowledge base, and the knowledge base is what an agent reaches — over MCP from a Foundry Agent Service agent, where it arrives as a tool like any other, or from Microsoft Agent Framework and your own code by calling the knowledge base REST API or the Azure AI Search SDKs.
  • Foundry IQ is Azure AI Search underneath, presented as one managed, permission-aware knowledge layer over several stores, so the agent gets a single MCP connection instead of one wiring job per source.
  • Watch the same signals here as anywhere else: ingestion quality, index freshness and whether the results coming back are actually relevant. An index that stopped refreshing three weeks ago still answers, confidently and wrongly.
In practice — a policy assistant
Ten years of policy PDFs sit in Blob Storage, half of them scans. The indexer cracks each file, the OCR skill reads the scanned pages, the Split skill cuts everything into 5,000-character chunks, integrated vectorization embeds each chunk, and output field mappings write chunk text and vector into the index. The agent then searches that index. Miss the OCR skill and exactly half the library is invisible — with no error anywhere to tell you.
The decision rule
Content that has to be searched points to an indexer plus a skillset. Enrichment Microsoft already ships points to a built-in skill; enrichment only you have points to a custom skill. Long documents point to chunking before embedding. Scans and photographs point to the OCR skill inside the pipeline. Several stores behind one agent points to Foundry IQ.

Extract content from documents

Approach Use it when
Document Intelligence prebuilt modelsThe document is a standard business type, so the fields come back with no training at all: invoice, receipt, ID, contract, health insurance card, US tax forms (W-2, W-4, 1040, 1095, 1098, 1099), bank check, bank statement, pay stub, credit card, marriage certificate and the US mortgage set. Alongside them sit the two document-analysis models: read for OCR, and layout for tables, selection marks and structure. On v4.0, layout can also return key-value pairs, which is what the old general document model used to do, though you have to ask for them with the keyValuePairs add-on on the request rather than getting them by default — that model is gone, and business card is deprecated. Both still turn up in older question banks.
Document Intelligence custom modelsThe form is yours, not a standard one. Custom template handles fixed layouts and needs as few as five labelled samples. Custom neural copes with layouts that vary. A composed model bundles several so one call picks the right one.
Content Understanding analyzersThe input is mixed media: documents, images, audio, video. Each analyzer extends one base analyzer for one of those content types — prebuilt-document, prebuilt-image, prebuilt-audio or prebuilt-video — but you define the field schema, and every analyzer returns the same shape of result, so one service, one pipeline and one downstream contract cover all four.
Generative extractionThe fields are unusual, the schema keeps changing, or the answer needs judgement rather than reading, such as "does this contract auto-renew". Ask for a defined JSON schema and validate what comes back.

Build and operate the pipeline

Build
  • Define the target schema first: field names, types, and which are required. The schema is the contract with the downstream system.
  • If you go with a custom model, you have to label the training data yourself, and your samples must cover the real range of layouts and scan quality the system will meet in production.
  • Extraction returns confidence scores per field. Set a threshold, and route anything below it to human review rather than accepting it silently.
  • Preserve bounding regions where available, so a reviewer can see where each value came from on the page.
  • Handle multi-page documents and batches asynchronously: you submit the job, then poll until the service says it has finished.
Operate
  • Validate extracted values against business rules, such as totals matching line items and dates falling in a plausible range.
  • Human in the loop for low-confidence or high-impact fields. When extraction gets a field wrong, a reviewer is the thing that catches it, and this is the standard mitigation.
  • Evaluate with the same discipline as Part 2: a labelled test set, per-field accuracy, and a baseline you re-measure after each change.
  • Extracted documents often contain personal information, so apply PII redaction, least-privilege access and retention rules.
  • Feed the structured output into search indexes or RAG. That is the join between this part and Part 5: what you extract here becomes the grounding data a model retrieves later.
The decision rule
Standard business document points to a prebuilt model. Proprietary form with a fixed layout points to custom template. Proprietary documents with varying layouts point to custom neural. Several document types through one endpoint points to a composed model. Mixed media in one pipeline points to Content Understanding. A field that requires judgement rather than reading points to a generative model with a validated schema.

Build agents, then run them in production

The two heaviest exam domains each contain a group of objectives that the six Learn modules barely touch: Build agents by using Foundry (part of the 30–35% domain) and Manage, monitor, and secure AI systems (part of the 25–30% domain). This part covers both.

Skill area 1

Build and orchestrate agents

An agent is three things saved together under one name, kept as a version you can point at: a model, the instructions that tell it what its job is, and the tools it may use. Save it once and every conversation gets the same behaviour. That is the whole definition, and every agent question comes down to those three parts, plus where the conversation history is kept and who decides what happens next.

In practice · a claims triage agent
Instructions: “You triage motor claims. Never approve a payment.” Tools: lookup_policy, estimate_repair, create_ticket. The model decides the order; your code runs the functions. The instruction about payment is in the agent, not in each prompt, so it cannot be forgotten on a busy day.

Three orchestration patterns

  • Sequential — each agent’s output feeds the next. Use it for a pipeline with fixed stages: extract, then validate, then summarise.
  • Group chat — whichever agent is needed next takes over, chosen by the context or by a rule you write. Use it for escalation and expert handoff, where you cannot say in advance who will be needed.
  • Human in the loop — the run pauses, asks a person, and waits before continuing.
In practice · when to reach for group chat
A support assistant answers billing questions itself, but hands anything about data deletion to a compliance agent. You cannot express that as a fixed sequence, because most conversations never need the second agent. Control passes on context, which is group chat.

Approvals and safeguards

Each tool carries an approval setting. When a tool needs approval, the run stops before that call is made: it hands back the name of the tool the model wants to use and the arguments it wants to pass, and then waits. The call happens only after the caller approves and resumes the run. The service pauses; it does not judge. Deciding whether the action should go ahead is the calling application’s job, not the service’s.

In practice · the rule of thumb
Anything that spends money, sends a message to a customer, or writes to a system of record gets an approval gate. Read-only lookups do not. If the scenario says “must be signed off”, the answer is tool approval, not a cleverer system message.

Evaluating an agent

Metrics that score the final answer do not tell you whether the agent went about the job properly. A separate family of evaluators looks at the behaviour instead. Each one scores a run and reports it as a pass or a fail against a threshold. Microsoft splits them into system evaluation, which judges the outcome, and process evaluation, which judges the steps and the tool calls. The list keeps growing; these four come up most:

  • Intent resolution — did it understand what was asked.
  • Task adherence — did it stay inside its instructions and constraints.
  • Tool call accuracy — right tool, right arguments.
  • Tool output utilization — did it actually use what the tool returned.
In practice · reading a failure
An agent gives a confident wrong answer. Tool call accuracy passes, tool output utilization fails: it called the right API and then ignored the result. That is a prompt problem, not an integration problem — and the two evaluators together are what tell you so.

Skill area 2

Manage, monitor and secure

Identity and access

  • Keyless first. Anyone holding a key gets full access to the resource, and no role assignment can narrow that. Sign in with Microsoft Entra ID instead, then disable local authentication so the keys stop working at all.
  • Least privilege by role. Give an application the narrowest role that lets it do its job. Foundry Agent Consumer only calls agent endpoints and is the least-privilege choice for an app that just uses an agent. Foundry User adds the data actions a developer needs to build and test one. Foundry Project Manager manages projects and publishes agents; Foundry Account Owner and Foundry Owner create accounts and deploy models. These were renamed from Azure AI User, Azure AI Project Manager, Azure AI Account Owner and Azure AI Owner, so older material and some portal screens still use the old names. Do not reach for the Cognitive Services roles or Azure AI Developer: they belong to other resources. Roles can also be assigned on a single agent, which grants that agent’s endpoint and nothing else.
  • Two network directions. Inbound: turn public network access off and reach the project through a private endpoint. Outbound: put agent traffic on a managed virtual network, so that when the agent calls your storage account, your search index and anything else it needs, that traffic stays off the public internet too.
In practice · the production shape
The app runs as a managed identity, holds no secret at all, reaches Foundry over a private endpoint, and has the role that permits calling the agent and nothing else. If a scenario mentions a key in an environment variable, that is the thing being tested.

Quotas, throttling and cost

Quota arrives as TPM (tokens per minute) and RPM (requests per minute). Your subscription gets an allowance for a given model in a given region, and every deployment you create draws from that same pool. Go over it and the service answers 429.

  • Retry with exponential backoff and jitter: wait a moment, then twice as long, then twice as long again, adding a small random offset so that every throttled client does not come back at the same instant. If the response carries a retry-after header, wait as long as it says.
  • Ask for more quota, or move the work onto provisioned throughput, which reserves capacity for you, when that capacity has to be guaranteed rather than shared.
  • Send work that is not time-critical to a batch deployment, which is half the price.
In practice · reading a 429
A nightly report job and a customer chat share one deployment, and the chat starts failing at 2am. The fix is not more retries — it is moving the report to batch so it stops competing for the same tokens.

Observability

Tracing uses OpenTelemetry, the standard way of recording what an application did step by step, and sends those records to Azure Monitor Application Insights. Connect an Application Insights resource to the project or nothing is recorded at all. A trace captures the input and the output, every tool call and what it returned, the tokens spent, and how long each step took.

  • Continuous evaluation scores a sample of live traffic as it happens.
  • Retrieval health is its own signal, separate from model quality: whether ingestion is still succeeding, how stale the index has become since the last indexer run, and whether what comes back still answers the question. An index that quietly stopped refreshing three weeks ago still returns results, and the model still sounds certain about them.
  • Scheduled evaluation re-runs the same fixed dataset on a timer. That is what catches drift: you keep the questions identical, so if the scores move, something else moved — the model, or the data it retrieves.
In practice · why both
Continuous evaluation tells you today’s users are unhappy. Scheduled evaluation against a frozen set tells you the system changed, because the questions did not. You need the second to know whether to roll back.

CI/CD

Create the resources and deploy hosted agents with the Azure Developer CLI, run from GitHub Actions or Azure DevOps. The pipeline signs in as a service principal, an identity that belongs to the pipeline rather than to a person. Gate the release on an evaluation run: make the pipeline evaluate the new version and stop the deployment if the scores drop, exactly as a failing unit test would stop it.

Part 10 in one line
An agent is a model plus instructions plus tools; the conversation holds what it remembers, and approvals decide what it is allowed to do. In production it runs as a managed identity with no keys, inside a quota you will eventually hit, and you can only see what it did if you connected Application Insights before you needed it.

Lab practice, and what survives the vendor race

Nobody knows whether Microsoft, Google, Amazon or a company that does not exist yet leads in three years. So learn the parts that move with you, and treat the Azure specifics as the current dialect rather than the language.

Transfers to any vendor
  • Prompt design, few-shot, chain of thought, structured output
  • The RAG pattern: chunk, embed, retrieve, augment, generate
  • Embeddings, vector search and cosine similarity
  • Tool and function calling, where the model asks for a call and your code makes it
  • Evaluation discipline: baseline, change one thing, re-measure
  • Working out what a design will cost, and how slow it will feel, in tokens
